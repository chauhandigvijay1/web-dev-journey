## The NoSQL Philosophy

DsSync Hub utilizes a Document-based database model powered by **MongoDB Atlas** and the **Mongoose ODM**. 

While a traditional SQL database provides strict relational integrity, we chose NoSQL to prioritize schema flexibility—an absolute necessity when storing the deeply nested, rich-text markdown JSON payloads generated by our collaborative Note and Chat modules.

---

## 🏗️ Entity Relationships

The core architecture revolves around the **Workspace** boundary to ensure strict multi-tenant isolation.

```text
User
 ├── owns many Workspaces
 ├── creates many Tasks
 ├── writes many Notes
 ├── sends many Messages
 └── has one Subscription

Workspace
 ├── has many Members (Users)
 ├── has many Tasks
 ├── has many Notes
 └── has many Messages
```

## 🗄️ Core Collections

### 1. `users`
Stores all account and authentication state.

```json
{
  "_id": "ObjectId",
  "fullName": "Shivani Singh",
  "username": "shivani",
  "email": "shivani@gmail.com",
  "password": "hashed_password",
  "phone": "9876543210",
  "avatar": "image_url",
  "provider": "local | google",
  "role": "user",
  "isVerified": true,
  "resetPasswordToken": "hashed_token",
  "resetPasswordExpires": "Date",
  "createdAt": "Date",
  "updatedAt": "Date"
}
```

### 2. `workspaces`
The multi-tenant organizational boundary.

```json
{
  "_id": "ObjectId",
  "name": "DsSync Team",
  "slug": "dssync-team",
  "owner": "UserId",
  "members": ["UserId"],
  "createdAt": "Date",
  "updatedAt": "Date"
}
```

### 3. `tasks`
The productivity engine.

```json
{
  "_id": "ObjectId",
  "workspace": "WorkspaceId",
  "title": "Build billing page",
  "description": "Design and integrate checkout",
  "status": "todo | in_progress | review | done",
  "priority": "low | medium | high | critical",
  "assignee": "UserId",
  "dueDate": "Date",
  "createdBy": "UserId",
  "createdAt": "Date",
  "updatedAt": "Date"
}
```

### 4. `notes`
Rich-text documentation.

```json
{
  "_id": "ObjectId",
  "workspace": "WorkspaceId",
  "title": "Sprint Notes",
  "content": "Rich text or markdown",
  "owner": "UserId",
  "createdAt": "Date",
  "updatedAt": "Date"
}
```

### 5. `messages` & `subscriptions`
Real-time chat logs and Razorpay billing statuses.

```json
// Messages
{
  "_id": "ObjectId",
  "workspace": "WorkspaceId",
  "sender": "UserId",
  "channel": "general",
  "message": "Hello team",
  "createdAt": "Date"
}

// Subscriptions
{
  "_id": "ObjectId",
  "user": "UserId",
  "plan": "free | pro",
  "status": "active",
  "provider": "razorpay",
  "paymentId": "optional",
  "startDate": "Date",
  "endDate": "Date"
}
```

*Note: `notifications` and `activities` collections are currently modeled for future scalability.*

## ⚡ Indexing Strategy

To guarantee rapid querying even with millions of documents, strict compound and unique indexes are applied. These ensure O(1) lookups during multi-tenant data access.

**Unique Indexes:**
- `users.email`
- `users.username`
- `workspaces.slug`

**Compound/Boundary Indexes:**
- `tasks.workspace`
- `tasks.status`
- `notes.workspace`
- `subscriptions.user`

> [!TIP]
> If you ever modify a Mongoose schema to include a new unique constraint, you must manually instruct MongoDB to apply it locally by running: 
> ```bash
> npm run sync:indexes
> ```

## 🛡️ Database Security Practices

- **Zero Plaintext**: Passwords and Reset Tokens are cryptographically hashed via bcrypt before ever touching the database.
- **Data Scrubbing**: Mongoose `.select()` projections are used strictly across all API endpoints to ensure sensitive data (like hashed passwords or stripe tokens) are stripped before the JSON response is sent to the client.
- **Stateless Tokens**: JWTs manage access control; no session secrets or IP addresses are stored permanently in the DB documents.
